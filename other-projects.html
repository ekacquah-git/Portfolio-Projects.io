Workforce Analytics

Professional builds at Spring Education Group

TA Conversion Report Investigation

The Talent Acquisition dashboard started showing conversion rates dropping in a way that did not match what the recruiting team was seeing day to day. When the people doing the work tell you the number is wrong, that is usually worth listening to. I traced it back through the pipeline and found a sourcing categorization issue that was misattributing candidates and throwing off funnel metrics across the board.

Before touching the model I asked the manager what numbers she expected and got specific recruiter and candidate names. Running the report against those confirmed the gap was real. Working up through the layers, the joins and filters were clean, which pointed at the source: recruiters were not consistently updating application status as candidates moved through the funnel. One recruiter's phone screen to first interview rate corrected from 40% to 60% once the missing updates were accounted for.

Once that was corrected I rebuilt the dashboard using Power BI's Key Insights feature, which flags statistically notable weekly changes in conversion rates, volume, and funnel drop-off on its own. That changed the character of the weekly VP review. The analysis was already done by the time everyone sat down, so the meeting could be about decisions.

Tools: Dayforce, SQL Server, Power BI, Power BI Key Insights

School Turnover Scorecard

Staff turnover across the school network was being tracked in aggregate, which meant a school could be in serious trouble for months before anyone upstream noticed. The EVP of Operations asked for a school-level scorecard covering all roles, with the lowest performers identified.

When the timeline compressed I assessed what could be built accurately in the window. Job class structure varied significantly by business line, and a full cross-company build under that constraint carried real risk of rate calculation errors where classification logic differed. I flagged that to the EVP and recommended anchoring on teachers and assistant teachers, the cleanest classification and the highest strategic priority, with the remaining role groups to follow in later iterations. He aligned.

The scorecard broke turnover rates, tenure distributions, and exit patterns down to the individual school, then rolled them up to region and network views. The bottom ten were flagged outright and a watch list caught schools approaching concerning thresholds.

Some schools came back above 200% turnover, which drew immediate pushback. I investigated before defending anything, and found a job title had been discontinued and renamed. The old title had dropped out of the headcount denominator, which artificially deflated the base. I documented the edge case, added a visible safeguard to the model, and reconvened with the EVP to walk through the cause before the scorecard drove any decisions. That conversation restored confidence in the data.

It became a yearly standing deliverable and a primary driver in the effort to reduce turnover, which came down 16% across our schools over the period it was in use.

Tools: Dayforce, ODATA, Power Query, Power BI

Bonus Allocation Model

Discretionary bonus allocations across a large employee population were being made without much consistent structure behind them. I built a model that applied objective criteria to the process, weighing performance metrics, tenure, and role classification, and put the results in a Power BI report managers could review and adjust inside defined parameters.

The complexity was two source streams. Standard bonus data came from Dayforce, and a separate program for one business line sat with Finance under different rules. I combined both into a unified SQL model feeding a dual-audience report. The executive view surfaced department-level year-over-year budget, allocation, and share with dollar flags for departments exceeding forecast. The manager view drilled to the employee level.

Because Dayforce was the direct source, allocations populated as they were approved through the year, which made it a live forecasting tool. At any point in the quarter leadership could see their current position and where the full fund was tracking to land by year end. That was the question driving the quarterly reviews with the CFO and VP of HR.

The Finance source arrived late on a recurring basis. When it did, I notified stakeholders immediately and the dashboard surfaced the absence explicitly, timestamping every load so nobody was deciding on an incomplete picture without knowing it.

A process that had been manual and largely undocumented became auditable and repeatable. Allocation decisions held up when leadership questioned them, which was the real point.

Tools: Dayforce, SQL, Power Query, Power BI

Snowpipe with Azure Blob Storage and AWS S3

Automated Pipeline Ingestion into Snowflake

Snowpipe watches a cloud storage container and loads files into Snowflake as they land, so the warehouse updates itself with nobody starting the job. I have built this against both Azure Blob Storage and AWS S3. The two clouds differ in the details, but the shape is the same in both: Snowflake generates an identity, you go approve that identity on the cloud provider's side, and then storage events trigger the load.

That approval step is the part worth understanding. Snowflake never holds your storage credentials. You create a storage integration, run DESC on it, and Snowflake hands back an identity it created for you. You take that identity to the cloud provider and grant it read access to the specific container you named. Until that grant exists, the integration is inert. The same handshake repeats for the notification path that triggers the loads.

Azure Blob Storage

The storage integration declares the tenant and the exact container Snowflake is allowed to reach. Running DESC on it returns a consent URL and a multi-tenant app name. Visiting that URL registers the Snowflake service principal in Azure Active Directory, and from there the app gets the Storage Blob Data Reader role scoped to the storage account. An external stage then points at the container and reads it directly.

The event side of Azure takes more assembly. Blob creation events go to Event Grid, which publishes them to a Storage Queue that you create. Snowflake reads that queue through a notification integration, which carries the queue URI and the tenant, and needs its own consent grant with the Storage Queue Data Contributor role. On the compliance model I ran three separate queues, one per source file, with a notification integration for each.

Each pipe then binds a queue to a table and filters with a pattern, so a file dropped into the container reaches only the table it belongs to. Three files, three queues, three pipes, and no cross-loading. SYSTEM$PIPE_STATUS confirms each one is running and shows the pending file count if a load backs up.

AWS S3

On AWS the storage integration names an IAM role rather than a tenant. Running DESC returns an IAM user ARN and an external ID that Snowflake generated for your account. Both go into the trust policy of that IAM role, which is what allows Snowflake to assume it. The role itself carries a policy granting read access to the bucket and prefix you specified.

S3 buckets and IAM provided the storage and the secure connection. On the Snowflake side I built the objects that receive and stage whatever comes through.

Those objects are the databases, schemas, and tables that sit at the end of the pipe. The notification path here is simpler than on Azure. You create the pipe with AUTO_INGEST enabled, and Snowflake provisions and manages an SQS queue on its own. SHOW PIPES returns that queue ARN, and you point an S3 event notification at it for object-created events. Snowflake owns the queue, so there is one less piece to maintain.

Once it was running, any new upload streamed straight through and became a live feed of new records. Being able to pause the pipe matters more than it sounds. It lets you hold ingestion while a source problem gets fixed, so bad data stays out of Bronze and you skip the cleanup entirely.

I used a similar setup to keep continuous watch on workforce wages and data integrity inside our HCM, which is where this pattern really proved itself.
