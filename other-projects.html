Data Cleaning in SQL

Nashville Housing · Reliable Analysis Starts with Clean Data

Cleaning and transformations are the unsung heroes in driving any analysis forward. Nobody puts them in a presentation, but every number downstream depends on them.

Goal: Getting the Nashville Housing dataset into a state where analysis is actually possible.

  • The first query tells you what you are dealing with. Missing values scattered throughout and records that do not line up the way you would want them to.
  • I cleaned and standardized the records to close the gaps and get the formatting consistent across the table.
  • Splitting the address into its own columns made the data readable and gave me something to filter on later.
  • A View handled the duplicate removal, which kept the raw data intact. Deleting from source is the kind of shortcut you regret two months later.
Key Insights:
  • Properties can have multiple owners, which matters a great deal if you are analyzing anything at the individual level.

Snowpipe with Azure Blob Storage and AWS S3

Automated Pipeline Ingestion into Snowflake

Snowpipe watches a cloud storage container and loads files into Snowflake as they land, so the warehouse updates itself with nobody starting the job. I have built this against both Azure Blob Storage and AWS S3. The two clouds differ in the details, but the shape is the same in both: Snowflake generates an identity, you go approve that identity on the cloud provider's side, and then storage events trigger the load.

That approval step is the part worth understanding. Snowflake never holds your storage credentials. You create a storage integration, run DESC on it, and Snowflake hands back an identity it created for you. You take that identity to the cloud provider and grant it read access to the specific container you named. Until that grant exists, the integration is inert. The same handshake repeats for the notification path that triggers the loads.

Azure Blob Storage

The storage integration declares the tenant and the exact container Snowflake is allowed to reach. Running DESC on it returns a consent URL and a multi-tenant app name. Visiting that URL registers the Snowflake service principal in Azure Active Directory, and from there the app gets the Storage Blob Data Reader role scoped to the storage account. An external stage then points at the container and reads it directly.

The event side of Azure takes more assembly. Blob creation events go to Event Grid, which publishes them to a Storage Queue that you create. Snowflake reads that queue through a notification integration, which carries the queue URI and the tenant, and needs its own consent grant with the Storage Queue Data Contributor role. On the compliance model I ran three separate queues, one per source file, with a notification integration for each.

Each pipe then binds a queue to a table and filters with a pattern, so a file dropped into the container reaches only the table it belongs to. Three files, three queues, three pipes, and no cross-loading. SYSTEM$PIPE_STATUS confirms each one is running and shows the pending file count if a load backs up.

AWS S3

On AWS the storage integration names an IAM role rather than a tenant. Running DESC returns an IAM user ARN and an external ID that Snowflake generated for your account. Both go into the trust policy of that IAM role, which is what allows Snowflake to assume it. The role itself carries a policy granting read access to the bucket and prefix you specified.

S3 buckets and IAM provided the storage and the secure connection. On the Snowflake side I built the objects that receive and stage whatever comes through.

Those objects are the databases, schemas, and tables that sit at the end of the pipe. The notification path here is simpler than on Azure. You create the pipe with AUTO_INGEST enabled, and Snowflake provisions and manages an SQS queue on its own. SHOW PIPES returns that queue ARN, and you point an S3 event notification at it for object-created events. Snowflake owns the queue, so there is one less piece to maintain.

Once it was running, any new upload streamed straight through and became a live feed of new records. Being able to pause the pipe matters more than it sounds. It lets you hold ingestion while a source problem gets fixed, so bad data stays out of Bronze and you skip the cleanup entirely.

I used a similar setup to keep continuous watch on workforce wages and data integrity inside our HCM, which is where this pattern really proved itself.
